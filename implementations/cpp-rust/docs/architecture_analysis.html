01这是个什么项目

bot4cj.cpp（仓颉版 bot4cj 的 C++17 移植；上游仓库 qingss0/bot4cj）是一个"用声明式脚本 + 脚本驱动"控制真实硬件的机器人控制框架——bot4cj（仓颉版）的 C++17 全量移植：三份脚本的设计与用法完全不变，底层运行时换成原生 C++（std::thread + LuaJIT C API）。

它把"硬件拓扑、驱动逻辑、动作编排"三者彻底解耦，分别用三种脚本来承载：

结构.sql（SQL4cj）

用 CREATE TABLE / INSERT 声明机器人有哪些硬件、挂在哪条总线、什么地址、什么控制器。解析阶段零资源占用，只建立"硬件变量表"。

驱动.lua（LuaJIT）

每个硬件一个 modules/X.lua，实现 build / call / destroy / read 生命周期。通过 HAL.lua 的 ffi.C 直调 glibc 落到内核设备文件。

动作.mt（mt2）

逐行 DSL：一帧 = 一行，列 <device.param> 是参数名。运行期 RobotStruct.run() 按列序逐行 play()，把参数发给硬件驱动。

核心价值主张

"不接任何硬件也能跑通全流程" —— 传感器桩替身（virtbus / dummy）与 Relay 转发链路，让 cat scripts/relay-test.mt | ./build/mybot --robot=robots/relay-test.sql 在裸机即可自校验。这是它区别于"必须挂硬件才能调试"的传统固件的根本优势。

入口 src/main.cpp（约 300 行，2026-09 快照）只做流水线编排与信号安装：装载结构脚本 → RobotStruct::active() → 动作流水线 run(stdin/TCP/文件) 或 MCP 后端流水线 → deactivate() 清理（参数解析/校验/帮助文本已下沉 cliargs.cpp）。真正的复杂度集中在硬件装配与派发层——robot.cpp 是编排门面（约 1100 行，含热 SQL 带电重装配），其五类职责按类拆在同层四个编译单元：注册表 hw_registry.cpp、元数据 meta_provider.cpp、装载+装配 hw_factory.cpp、动作派发 action_runner.cpp（含纯计算单点 ActionPlan::build）；再往下是硬件变量层（luavar.cpp / daemonvar.cpp 等）。

agent 体系为两进程架构（2026-09-24 起）：C++ 宿主唯一形态是 mybot --mcp-backend——硬件上电常驻，经 AF_UNIX socket 提供 MCP 工具后端（mcpbackend.cpp 帧协议 + socket 占用探测防双实例）；模型循环在独立 Rust 进程 mybot-agent（agent/，rig 0.42 直连 provider：reqwest + rustls），承载 REPL / --task / 会话持久化，经 socket 调用工具。旧 --agent（C++ 内嵌 agentloop/agentdriver）已删除。

03数据流 / 时序展开（一次 play 动作）

把"管道输入一帧 .mt"到"内核设备文件落盘"的完整调用链展开成四个纵向阶段，并把 @Daemon 并发旁路（经 600B 共享槽）画在同一张图上。

主路径（串行）四阶段

阶段发生位置做什么
① 解析入栈main.cpp → sqlparse / matrix / actionsource读入 .sql 与 .mt（stdin/TCP/文件）→ 解析成矩阵对象；按变量声明行（.sql 硬件表行、.mt 里的 @Vars/@Alias 行）各建一个硬件变量；active() 按声明序逐个 build()
② 逐帧播放robot.cpp · run_action按列序收集设备名（@Alias 解析穿透）→ 取参数 Json → hv.play(params) → ensureOk（ERR 即中断）→ $ 列 / controller 转发

返回路径的"双出口"

Lua 驱动返回的 table 经 lua_value_to_json 转 JsonValue：顶层设备直接出结果；带 controller 列的设备则把 {元数据 ∪ 自身返回表} 转发给下游控制器继续 play()。这是"传感器 → 滤波 → 执行器"链路的底层支撑。

04内容组合：六大核心机制

架构的"骨架"由六条机制撑起来，理解它们 = 理解整个框架。这也是扩展开发时最该优先触碰的"杠杆点"。

M1两阶段构造

解析期零资源（不 open fd、不分配 lua_State）；active() 才按声明序（HwRegistry::seq_）build；deactivate() 反序 destroy。I2C 总线 → PCA9685 的 fd 依赖靠此顺序保证（先建总线再建挂在它上面的器件）。

M2驱动契约（halt-on-error）

每个驱动返回 {result="OK"/"ERR", message}；基类 MatrixVars_Hardware.ensureOk 见到 ERR 直接 throw，中断整条动作序列。语义统一、故障传播明确。

M3@Daemon 守护线程

std::thread 原生线程 + 独立 lua_State（jit.off），逐拍采样后写入 600B 共享内存槽（values[64]@72 / stop@584 / status@588 / quiesce@592）。主线程 play() 加锁读槽。join 超时走「弃管 + 槽位由线程自释放」的安全取舍，退出时如实告警弃管数量。

M4$ 引用列 + controller

元数据列以 $ 开头（如 $imu0）= 引用另一硬件 read() 的实时快照；裸名=字面量。可串成 imu0 → kf0 → mon0 三级"采样→滤波→消费"链。controller 让任意矩阵把 {元数据∪返回} 转发给下游。

M5HAL ffi.C 直调 + 可 mock 层

HAL.lua 用 ffi.cdef 声明 glibc 与 spidev ABI，布局自检（sizeof(spi_ioc_transfer)==32、cj_i2c_msg==16）。HAL.sys.* 间接层 + I2C_RDWR 原子事务，使桩替身可整体替换 26 个全局 i2c_*/spi_*/uart_* 函数（virtbus.lua 的 VFUNCS：12 + 9 + 5）。

M6MetaProvider（元数据闭包）

静态列在首次 collect 时冻结缓存；$ 引用列每次 play 做实时 read() 快照。避免每次调用重算全部字面列（首采冻结、之后浅拷贝重放），是播放性能的关键优化。

可测试性资产（三层守门体系）

测试约定：test/test_<driver>.lua 先 dofile("modules/X.lua") 加载真实 HAL，再覆盖全局 i2c_*/spi_*/milli_sleep；位运算/CRC 走 modules/bitcompat.lua（别名 bitc）。C++ 层单测与被测程序共用同一套源文件（test/cpp/，零第三方框架）。

当前守门规模：Lua/e2e 回归 260+ 通过（真机用例 i2c 与 video 按需跳过）+ C++ 单测 634 通过；CI 另有 ASan/UBSan 硬门禁，TSan / clang / clang-tidy / 覆盖率 / musl 五条亦为硬门禁（2026-09-25 起全部转硬），以及 ioctl/termios/V4L2 常量编译期自检（F-24 同族）。本页数字是2026-09 约数快照：权威口径一律以 bash test/run_all.sh 与 ./build/mybot_tests 的实时输出为准。

05架构体检：优势与边界

✔ 优势（加码的底气）

  • • 三脚本彻底解耦，加新硬件 = 加 1 张 .sql 表 + 1 个 .lua，零核心改动
  • • 不接硬件可跑全流程，CI/桩测试成本低
  • • halt-on-error + 反序 destroy，故障传播与资源回收干净
  • • @Daemon + $ 引用链，原生支持"采样→滤波→消费"多传感器流水线
  • • HAL 可 mock 层 + virtbus，任意驱动无真机可验证
  • • 驱动层用 Lua（迭代快），核心层 C++17（编译型、类型安全、零第三方 C++ 依赖）

✕ 边界 / 待补（加码的靶点）

  • • 仅 Linux + LuaJIT（HAL 依赖 glibc ffi 与 /dev 设备文件），无跨 OS 抽象
  • • 守护线程一线程一 Lua 状态，多守护场景内存与启动开销线性上涨
  • • 模型在线动作生成（DRL/CNN）尚未接入主流程（nn.lua 提供基础算子）
  • • 共享槽固定 64 值（values[64]），复杂多路并发有上限
  • • 安全沙箱是"护栏非安全边界"（中和 os.execute 等，非强隔离）
  • • 驱动生态依赖人工逐器件编写，缺自动 codegen / 统一描述语言
  • • 全部十条 CI job 均为硬门禁（2026-09-25 起）；后续关注跨 OS HAL 后端与驱动自动 codegen

关键风险：共享槽 64 值上限 & join 超时弃管

daemon_slot_t 的 values[64] 意味着单个守护最多并发暴露 64 个数值通道；join 超时会放弃 join、槽位由守护线程退出时自释放以防 UAF —— 这是有意的安全取舍，退出路径会如实告警弃管数量。扩展时若做多路传感器聚合，需要把该上限参数化或改为定长数组 + 索引引用。

06扩展开发路线图（五阶段加码）

按"低成本撬动最大收益"排序，五阶段自内向外：先加固已有的杠杆点（驱动扩展、并发扩展），再开新通道（网络、多 OS），最后接上 README 已点名的智能动作生成。

1

驱动生态扩展 低成本 · 高收益

新增硬件 = 1 张 .sql 表 + 1 个 modules/X.lua（build/call/destroy 三函数 + drv_common 复用）+ 1 个 test_<driver>.lua 离线桩测试。扩展动作：统一驱动描述语言（YAML/JSON 的"器件数据表"），配 virtbus 生成桩测试骨架，把"人工逐器件写"降为"填表 + 代码生成"。

2

并发 / 多路传感器聚合 中成本 · 高收益

@Daemon 现有 64 值上限（SLOT_MAXVALS=64，见 src/daemonvar.hpp；65+ 字段在加载期即被拒）。扩展动作：把 SLOT_MAXVALS 参数化（定长数组 + 索引引用，或链表），sensor_daemon.lua 已支持任意 build/call/destroy 驱动的"万能采样 chunk"，可加多守护聚合器（一路守护聚合多路 sensor 输出到同一槽位组），支撑"多 IMU + 多气感 + 里程计"复杂流水线。

3

网络 / 服务化动作传输 已落地 · 可再增强

已落地：动作输入源已抽象为可替换的 ActionSource（src/actionsource.cpp），管道 / TCP（--tcp，跨机强制口令）/ 文件（--input）三源等价，TCP 空闲超时与连接总时长预算防慢滴。后续增强：多连接 / WebSocket / 远端遥操 + 本地滤波分级，驱动层零改动。

4

跨 OS 抽象（HAL 后端可插拔）高成本 · 广覆盖

后端接口化已落地：HAL.lua 只留总线函数单点与 HAL.sys.* 契约，按 BOT4CJ_HAL_BACKEND dofile 后端，加载期逐项断言契约函数齐全（缺函数 fail-fast）；ffi 直调 glibc 的实现落在 modules/lib/hal_backend_glibc.lua，test_hal_backend_swap.lua 锚定换后端语义。待补：macOS libsystem / Windows / 纯仿真后端，以及各后端自己的路径白名单规则——驱动层不用改。

5

神经网络动作生成（nn）高成本 · 终极加码

modules/lib/nn.lua 已提供基础算子，DRL / CNN 动作生成仍待接入主流程：把"动作生成"从 .mt 手写脚本升级为模型在线推理。落地路径：在 C++ 核心层新增 NN 硬件变量类（对标 luavar 的 Lua 驱动变量加载）；动作 = 模型输出经 controller 转发到执行器。mybot-agent 的 capture_image 视觉工具链已为多模态观测铺路，可与阶段 2 的多传感器聚合组合成闭环强化学习机器人。

阶段依赖关系

1（驱动生态）→ 2（并发聚合）是"横向扩能力"，可先做且互相独立；3（网络）与 4（多 OS）是"通道与平台"，为 5（智能）铺路；5（NN）依赖 2（观测）+ 3（在线）。建议顺序：1 → 2 → 3 → 4 → 5，其中 1/2 可在当前 dev 分支独立开工，风险最低。
