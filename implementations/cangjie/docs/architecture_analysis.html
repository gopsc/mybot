01这是个什么项目

bot4cj 是一个"用声明式脚本 + 脚本驱动"控制真实硬件的机器人控制框架。它把"硬件拓扑、驱动逻辑、动作编排"三者彻底解耦，分别用三种脚本来承载：

结构.sql（SQL4cj）

用 CREATE TABLE / INSERT 声明机器人有哪些硬件、挂在哪条总线、什么地址、什么控制器。解析阶段零资源占用，只建立"硬件变量表"。

驱动.lua（LuaJIT）

每个硬件一个 modules/X.lua，实现 build / call / destroy / read 生命周期。通过 HAL.lua 的 ffi.C 直调 glibc 落到内核设备文件。

动作.mt（mt2）

逐行 DSL：一帧 = 一行，列 <device.param> 是参数名。运行期 RobotStruct.run() 按列序逐行 play()，把参数发给硬件驱动。

核心价值主张

"不接任何硬件也能跑通全流程" —— 传感器桩替身（virtbus / dummy）与 Relay 转发链路，让 cat action.mt | main --robot relay-test.sql 在裸机即可自校验。这是它区别于"必须挂硬件才能调试"的传统固件的根本优势。

入口极薄（src/main.cj 约 180 行）：解析 --robot → RobotStruct(file).active() → run(stdin) → finally deactivate()。真正的复杂度集中在 r.cj（RobotStruct，519 行）与 src/HV/ 四个硬件变量类。

03数据流 / 时序展开（一次 play 动作）

把"管道输入一帧 .mt"到"内核设备文件落盘"的完整调用链展开成四个纵向阶段，并把 @Daemon 并发旁路（经 208B 共享槽）画在同一张图上。

主路径（串行）四阶段

阶段发生位置做什么
① 解析入栈main.cj → SQL4cj / mt2stdin 读 .mt；.sql 解析建矩阵；每行 .mt 建一个 @Action 变量；按 hwSeq 序 active() 逐个 build()
② 逐帧播放r.cj · run_action按列序收集设备名 → 取参数 Json → hv.play(params) → ensureOk（ERR 即中断）→ $ 列 / controller 转发
③ Lua 驱动MtVars_Lua · call_lua元数据+参数合并进 obj → 注入 mode → Lua_pcall → 驱动局部变量 → HAL 全局函数 → HAL.sys.* 间接层（可 mock）
④ 系统落盘glibc → /dev → 内核 → 硬件ffi.C open/ioctl（路径白名单+数值校验）→ 设备文件 → I2C_RDWR 原子事务 → 物理器件；返回 {result,value} 逆向校验

返回路径的"双出口"

Lua 驱动返回的 table 经 lua_value_to_json 转 JsonValue：顶层设备直接出结果；带 controller 列的设备则把 {元数据 ∪ 自身返回表} 转发给下游控制器继续 play()。这是"传感器 → 滤波 → 执行器"链路的底层支撑。

04内容组合：六大核心机制

架构的"骨架"由六条机制撑起来，理解它们 = 理解整个框架。这也是扩展开发时最该优先触碰的"杠杆点"。

M1两阶段构造

解析期零资源（不 open fd、不分配 lua_State）；active() 才按 hwSeq 声明序 build；deactivate() 反序 destroy。I2C 总线 → PCA9685 的 fd 依赖靠此顺序保证（先建总线再建挂在它上面的器件）。

M2驱动契约（halt-on-error）

每个驱动返回 {result="OK"/"ERR", message}；基类 MatrixVars_Hardware.ensureOk 见到 ERR 直接 throw，中断整条动作序列。语义统一、故障传播明确。

M3@Daemon 守护线程

仓颉 spawn 绿色线程 + 独立 lua_State（jit.off），逐拍采样后写入 208B 共享内存槽（mutex@0, count@64, nvals@68, values[16]@72, stop@200）。主线程 play() 加锁读槽。拍间用仓颉 sleep 让出 worker，不做 ffi usleep 自旋。

M4$ 引用列 + controller

元数据列以 $ 开头（如 $imu0）= 引用另一硬件 read() 的实时快照；裸名=字面量。可串成 imu0 → kf0 → mon0 三级"采样→滤波→消费"链。controller 让任意矩阵把 {元数据∪返回} 转发给下游。

M5HAL ffi.C 直调 + 可 mock 层

HAL.lua 用 ffi.cdef 声明 glibc 与 spidev ABI，布局自检（sizeof(spi_ioc_transfer)==32、cj_i2c_msg==16）。HAL.sys.* 间接层 + I2C_RDWR 原子事务，使桩替身可整体替换 12 个全局 i2c_*/spi_* 函数。

M6MetaProvider（元数据闭包）

静态列在首次 collect 时冻结缓存；$ 引用列每次 play 做实时 read() 快照。消除每调用 O(cols·rows) 的全表扫描，是播放性能的关键优化。

可测试性资产（离线桩测试体系）

测试约定：test/test_<driver>.lua 先 dofile("modules/X.lua") 加载真实 HAL，再覆盖全局 i2c_*/spi_*/milli_sleep；位运算/CRC 走 modules/bitcompat.lua（别名 bitc）。当前回归 58 通过 / 0 失败，覆盖 INA219/INA3221/SHT3X/LTC2944/MAX17043/TPL0501 等已补齐驱动的离线桩测试。

05架构体检：优势与边界

✔ 优势（加码的底气）

  • • 三脚本彻底解耦，加新硬件 = 加 1 张 .sql 表 + 1 个 .lua，零核心改动
  • • 不接硬件可跑全流程，CI/桩测试成本低
  • • halt-on-error + 反序 destroy，故障传播与资源回收干净
  • • @Daemon + $ 引用链，原生支持"采样→滤波→消费"多传感器流水线
  • • HAL 可 mock 层 + virtbus，任意驱动无真机可验证
  • • 驱动层用 Lua，迭代快；核心层仓颉，编译型、类型安全

✕ 边界 / 待补（加码的靶点）

  • • 仅 Linux（glibc + /dev + sysfs + gpiod），无跨 OS 抽象
  • • 动作只走 stdin 管道（.mt），无网络/服务化传输
  • • 神经网络/DRL/CNN 动作生成仍是 README 里的 TODO（nn4cj 未接）
  • • 共享槽固定 16 值（SLOT_MAXVALS=16），复杂多路并发有上限
  • • 安全沙箱是"护栏非安全边界"（中和 os.execute 等，非强隔离）
  • • 驱动生态依赖人工逐器件编写，缺自动 codegen / 统一描述语言

关键风险：共享槽 16 值上限 & join 超时弃 join

daemon_slot_t 的 values[16] 意味着单个守护最多并发暴露 16 个数值通道；joinTimeout = max(5×interval, 2000ms) 超时会放弃 join、保留 slot 指针以防 UAF —— 这是有意的安全取舍，但扩展时若做多路传感器聚合，需要把该上限参数化或改为定长数组 + 索引引用。

06扩展开发路线图（五阶段加码）

按"低成本撬动最大收益"排序，五阶段自内向外：先加固已有的杠杆点（驱动扩展、并发扩展），再开新通道（网络、多 OS），最后接上 README 已点名的智能动作生成。

1

驱动生态扩展 低成本 · 高收益

新增硬件 = 1 张 .sql 表 + 1 个 modules/X.lua（build/call/destroy 三函数 + drv_common 复用）+ 1 个 test_<driver>.lua 离线桩测试。扩展动作：统一驱动描述语言（YAML/JSON 的"器件数据表"），配 virtbus 生成桩测试骨架，把"人工逐器件写"降为"填表 + 代码生成"。

2

并发 / 多路传感器聚合 中成本 · 高收益

@Daemon 现有 16 值上限。扩展动作：把 SLOT_MAXVALS 参数化（定长数组 + 索引引用，或链表），sensor_daemon.lua 已支持任意 build/call/destroy 驱动的"万能采样 chunk"，可加多守护聚合器（一路守护聚合多路 sensor 输出到同一槽位组），支撑"多 IMU + 多气感 + 里程计"复杂流水线。

3

网络 / 服务化动作传输 中成本 · 新通道

README 点名的 TCP 动作传输：把"stdin 管道读 .mt"抽象成可替换的 ActionSource 接口（管道 / TCP / WebSocket / 文件），让上位机 / 手机 / 边缘网关可远程下发动作帧。核心改动集中在 r.cj · run() 的 input 读取处，驱动层零改动。配合 controller 转发可实现"远端遥操 + 本地滤波 + 本地执行"分级。

4

跨 OS 抽象（HAL 后端可插拔）高成本 · 广覆盖

HAL 已用 ffi.C 集中收敛系统调用，扩展动作：把 HAL.sys.* 间接层抽成后端接口（glibc / macOS libsystem / Windows winsock+cygwin / 仿真桩）。驱动层不变，只换 sys 后端 + 路径白名单规则即可移植到 RPi / 桌面 / 容器化仿真。仿真桩 = 现成的 virtbus 思路放大。

5

神经网络动作生成（nn4cj）高成本 · 终极加码

README 明确 TODO 的 DRL / CNN 动作生成：把"动作生成"从 .mt 手写脚本升级为模型在线推理。落地路径：在仓颉核心层新增 MtVars_NN 变量类（对标 MtVars_Lua），把 main.cj 里注释掉的 NN/DRL 代码接活；动作 = 模型输出经 controller 转发到执行器。可与阶段 2 的多传感器聚合（观测向量）+ 阶段 3 的网络下发（在线更新）组合成闭环强化学习机器人。

阶段依赖关系

1（驱动生态）→ 2（并发聚合）是"横向扩能力"，可先做且互相独立；3（网络）与 4（多 OS）是"通道与平台"，为 5（智能）铺路；5（NN）依赖 2（观测）+ 3（在线）。建议顺序：1 → 2 → 3 → 4 → 5，其中 1/2 可在当前 dev 分支独立开工，风险最低。
