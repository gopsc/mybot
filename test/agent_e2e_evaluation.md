## 历史评估依据（截至 2026-10-07）

> 以下各节保留当日的 Phase 28 评估记录；其中的行数、场景编号、helper、守门位置和结论均为历史口径，不用于描述现状。

### 1. 文件性质特殊

agent_e2e.sh 是**端到端测试脚本**，不是守门框架代码。它的特点：

- **场景驱动**：每个 R1-R14 场景是一个完整的端到端测试，包含 setup/执行/验证/teardown 全流程
- **状态耦合**：场景间共享临时目录、socket 路径、进程状态，抽取会破坏内聚性
- **证据链完整**：每个场景的注释、断言、错误处理都在同一文件内，便于追溯

### 2. 抽取收益低

- **无重复代码**：14 个场景（R1-R14）各自测试不同性质，代码形态差异大，无可抽取的公共模式
- **无共享逻辑**：场景间的 helper 函数（如 wait_for_log、check_audit）已是最小必要集合
- **读取成本可控**：1613 行虽长，但按场景分段（每段 80-120 行），导航成本低

### 3. 抽取风险高

- **破坏证据链**：端到端测试的价值在于「一个文件看完整故事」，抽取后需跨文件追踪
- **状态管理复杂化**：场景共享的临时目录、socket、进程生命周期会变得难以追踪
- **反向验证困难**：Phase 28 的核心约束是「搬迁不改写」，但 agent_e2e.sh 的抽取必然涉及状态传递的重构

### 4. 与守门框架的边界清晰

agent_e2e.sh 与 run_all.sh 的关系是**调用方-被调用方**：

- run_all.sh 只调用 `bash scripts/agent_e2e.sh --rust`，不关心内部实现
- agent_e2e.sh 内部的状态管理、场景编排是端到端测试的实现细节
- 守门框架的抽取（Phase 28 ①③④）已完成，agent_e2e.sh 不在抽取范围内

## 历史替代方案评估（留档）

### 方案 A：按场景拆分成 14 个文件

**否决原因**：
- 场景间共享临时目录清理逻辑，拆分后需引入全局状态管理
- R11（两进程接力）与 R12/R13（协议差异）有共享的 socket 路径约定，拆分后需跨文件协调
- 读取成本从「一个文件滚动」变成「14 个文件跳转」，反向增加

### 方案 B：抽取公共 helper 到独立文件

**否决原因**：
- wait_for_log、check_audit 等 helper 只被 1-2 个场景使用，抽取后增加文件跳转
- helper 与场景的上下文强耦合（如特定的日志格式、审计字段），抽取后需传大量参数
- 端到端测试的 helper 不同于守门框架的 record_pass/record_fail，前者是测试逻辑的一部分

### 方案 C：保持现状，加强注释导航

**采纳原因**：
- 文件头部已有完整的场景索引（R1-R14 的用途说明）
- 每个场景以 `# R<N> ` 开头的注释块分隔，grep 可快速定位
- 与 Phase 28 的核心目标（守门框架抽取）不冲突
